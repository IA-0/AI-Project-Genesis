# ADR-0001 — Atlas se mantiene como proyecto de Fase 2 (con recortes de alcance explícitos)

- **Estado:** Aceptado (revisado por Federico, 2026-07-06)
- **Fecha:** 2026-07-06
- **Decisores:** Fable (Claude Code) como Chief Architect · revisión y aprobación final: Federico
- **Insumos:** `docs/context/PROJECT_BRIEF.md`, `<evaluation_criteria>` de `docs/prompts/MASTER_PROMPT.md`

## Contexto

La misión es encontrar el proyecto open source con mayor potencial real de impacto en la carrera de Federico (entrevistas/empleo en IA, Software Engineering, Automatización o Análisis Funcional). Atlas — un orquestador de agentes de IA que convierte una frase de negocio en especificación funcional, arquitectura y backlog ejecutable — es la hipótesis de partida. Este ADR la somete a los cinco criterios de evaluación; si alguno falla, el veredicto debe decirlo y proponer recorte o reemplazo.

Restricciones activas: una sola persona, 4 días de trabajo part-time para la Fase 2, stack ya validado (Python, Groq, Claude Code, Docker, n8n, VPS Oracle Free Tier), y una debilidad de diseño conocida — se empiezan muchos proyectos y se terminan pocos, así que todo plan que dependa de más de 4-5 días de foco continuo es de alto riesgo.

<analisis>

**Criterio 1 — ¿Resuelve un problema real y verificable? PASA.**
El gap entre "idea de negocio en una frase" y "algo construible" (historias de usuario, modelo de datos, backlog) es un dolor documentado de developers independientes y PyMEs, y Federico lo sufrió en primera persona construyendo automatizaciones para clientes: el cliente tiene la idea, nadie tiene la spec. Es verificable porque el MVP se prueba contra un caso de uso real de esa experiencia. Matiz honesto: problema real no implica mercado vacío — hay wrappers de "generador de PRD" por todos lados. La diferenciación de Atlas es doble: el output es un repo ejecutable por un agente de código (no un documento suelto), y el pipeline expone criterio de ingeniería (roles, verificación, trazabilidad). Para la misión (carrera, no dominar un mercado), el criterio se sostiene incluso en espacio concurrido.

**Criterio 2 — ¿Es defendible técnicamente en una entrevista de 45 minutos? PASA, con una condición.**
La superficie de trade-offs defendibles es rica y no trivial: enrutamiento rol→modelo por costo/capacidad (Groq para roles mecánicos, Claude para criterio), pipeline secuencial vs. paralelización (qué artefactos dependen del anterior y cuáles no), validación de outputs entre agentes (verificación cruzada), y el repo como memoria compartida del circuito. Además tiene narrativa doble para el perfil buscado: el producto *automatiza análisis funcional*, así que defenderlo es a la vez demostrar análisis funcional. La condición: cada trade-off debe quedar documentado en un ADR en el momento en que se decide — el material de defensa es la traza de decisiones, no el volumen de código. Sin esa disciplina, el criterio falla en la práctica.

**Criterio 3 — ¿Puede quedar funcional en 4 días part-time de una persona? PASA SOLO CON RECORTE — es el criterio de mayor riesgo.**
El sistema genérico ("cualquier idea de negocio"), no. El MVP del brief (un solo caso de uso, pipeline end-to-end, salida Markdown a un repo, sin UI, sin multi-tenant), sí: es Python + llamadas a APIs + plantillas de artefactos, sin tecnología nueva. Para que el criterio aguante se fijan además estos recortes, que este ADR hace vinculantes:
1. **Descubrimiento one-shot:** el motor de preguntas genera el set mínimo, Federico responde una vez, y el pipeline sigue. El loop interactivo multi-turno queda post-MVP.
2. **Deploy fuera del MVP:** la demo corre local (Docker opcional). El VPS Oracle es target post-MVP, no criterio de "funciona".
3. **Cierre diario tangible** (ya en el master prompt): cada día termina con algo que corre o se lee; si el día 4 se complica, se recorta pulido de demo, nunca el pipeline end-to-end.
Este es el criterio que la debilidad conocida (empezar mucho, terminar poco) puede romper; los tres recortes existen exactamente para eso.

**Criterio 4 — ¿Genera algo mostrable en LinkedIn en la primera semana? PASA.**
El antes/después es inherentemente visual y narrable: entra una frase de negocio, sale un repo con spec funcional, arquitectura y backlog priorizado. Eso se muestra en un video corto o capturas en el post del Día 4. La métrica verificable con fecha vive en `NORTH_STAR.md` (2026-07-10).

**Criterio 5 — ¿La arquitectura demuestra criterio real de ingeniería? PASA.**
Atlas es isomorfo a su propio método de construcción: se construye orquestando una flota con los mismos principios que su pipeline interno aplica (enrutamiento por costo/capacidad, verificación cruzada, repo como memoria). Los trade-offs a explicitar en la Fase 2 Día 2 ya son visibles: por qué secuencial donde cada rol consume el artefacto del anterior y dónde paralelizar, por qué cada rol va al modelo que va, cómo se valida el output de un agente antes de que el siguiente lo consuma. Nada de eso es decoración: son decisiones con alternativas reales y costos medibles.

</analisis>

## Decisión

**Atlas se mantiene** como proyecto de la Fase 2, condicionado a los tres recortes vinculantes del Criterio 3 (descubrimiento one-shot, deploy post-MVP, cierre diario tangible) y a la disciplina de ADRs del Criterio 2.

## Consecuencias

- `NORTH_STAR.md` fija la métrica verificable con fecha 2026-07-10.
- La Fase 2 arranca según el timebox del master prompt (Día 1: descubrimiento + funcional; Día 2: arquitectura; Día 3: implementación mínima repartida en la flota; Día 4: demo + LinkedIn).
- Backlog post-MVP explícito: loop de descubrimiento interactivo, UI, multi-tenant, deploy a VPS, más casos de uso, gestión de sprints.
- Riesgo principal aceptado: deslizamiento del timebox por la debilidad conocida. Mitigación: recortes vinculantes + entregable tangible diario. Si el día 4 no hay pipeline end-to-end, este ADR se revisa (no se extiende en silencio).

## Verificación

El flujo original pedía que otro modelo de la flota (Codex CLI) revisara el `<analisis>` antes del commit. Se intentó el 2026-07-06 y se descartó: el sandbox de Codex en Windows no pudo leer el repo (error de permisos al crear procesos), y Federico decidió simplificar el mecanismo. **El revisor de este ADR es Federico**, que lo lee completo antes de dar por cerrado el checkpoint de Fase 1. El principio de fondo no cambia: la decisión no se acepta sin una revisión independiente de quien la escribió.

**Resultado de la revisión (2026-07-06):** aprobado con dos ajustes — mostrar `NORTH_STAR.md` completo antes del commit, y alinear `<phase_2_atlas>` Día 2 del master prompt con el recorte 2 (deploy real post-MVP). Ambos aplicados en el mismo commit que acepta este ADR.
